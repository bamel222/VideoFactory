Commandes OVHCloud

L'ensemble des commandes utilisées pour déployer et exploiter l'application sur l'instance Public Cloud, dans l'ordre logique, avec explications.

Contexte : l'application tourne avec Docker Compose (6 conteneurs : redis, postgres, backend, worker, frontend, nginx). Le code vit dans ~/VideoFactory. La clé SSH privée est sur votre PC dans C:/Users/ToshR/Downloads/ovh_cle_ssh_privee.pem.

01Connexion au serveur (SSH)

# Depuis votre PC (PowerShell ou Git Bash sur Windows) ssh -i C:/Users/ToshR/Downloads/ovh_cle_ssh_privee.pem ubuntu@57.130.39.132

Le -i pointe vers votre clé privée SSH (fichier .pem), puis ubuntu@ suivi de l'IP publique de l'instance.

Astuce : pour éviter de retaper le chemin de la clé à chaque fois, créez un alias (dans PowerShell, éditez $PROFILE) ou placez la clé dans ~/.ssh/.

02⭐ LA commande de mise à jour (à retenir absolument)

À lancer à chaque fois que du nouveau code est poussé sur GitHub. Elle récupère le code, reconstruit les images, puis recrée nginx (pour qu'il recharge sa config — c'est ce qui évite les « 502 »).

Commande magique — mise à jour complète
cd ~/VideoFactory git pull docker compose -f infra/docker-compose.deploy.yml --env-file infra/.env up -d --build docker compose -f infra/docker-compose.deploy.yml up -d --force-recreate nginx
Important : attendre la fin complète du --build (retour au prompt) avant de tester. Pendant le build, le site peut renvoyer un 502 — c'est normal et temporaire.

Détail de chaque ligne :

  • git pull — télécharge les derniers changements depuis GitHub.
  • up -d --build — reconstruit les images Docker et redémarre les conteneurs modifiés.
  • --force-recreate nginx — recrée nginx pour qu'il charge la config à jour (sinon il garde l'ancienne adresse des services → 502).

03Installer Docker (une seule fois, à la création de l'instance)

sudo apt-get update sudo apt-get install -y docker.io docker-compose-plugin sudo usermod -aG docker $USER # se déconnecter puis se reconnecter pour activer le groupe docker exit

04Récupérer le code (une seule fois)

git clone https://github.com/bamel222/VideoFactory.git cd VideoFactory
Le repo est privé : la première fois, git vous demande un identifiant. Utilisez votre nom d'utilisateur GitHub + un token d'accès (pas votre mot de passe).

05Configuration secrète (une seule fois)

cd ~/VideoFactory/infra cp .env.production.example .env nano .env

Générer les deux secrets obligatoires (à coller dans le .env) :

openssl rand -base64 32 # → ENCRYPTION_KEY openssl rand -base64 32 # → JWT_SECRET

06Vérifier l'état des services

cd ~/VideoFactory docker compose -f infra/docker-compose.deploy.yml ps

Doit afficher 6 conteneurs en Up (et healthy pour postgres, redis, backend).

07Consulter les logs

# Logs du backend (démarrage, migrations, erreurs API) docker compose -f infra/docker-compose.deploy.yml logs backend --tail 50 # Suivre les logs en direct (Ctrl+C pour quitter) docker compose -f infra/docker-compose.deploy.yml logs -f backend # Logs du worker (suivi de la génération vidéo) docker compose -f infra/docker-compose.deploy.yml logs -f worker # Logs du frontend (erreurs de build Next.js) docker compose -f infra/docker-compose.deploy.yml logs frontend --tail 50

Le worker exécute le pipeline vidéo : c'est lui qu'on suit pendant une génération.

08Tester l'API (le test qui ne ment pas)

# Le login doit renvoyer du JSON (avec "access_token"), jamais du HTML curl -s -X POST http://localhost/api/v1/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"owner@vf.ai","password":"password123"}'

Si ça renvoie <html>...502...</html>, le backend n'est pas joignable → refaire la commande de mise à jour (section 02).

09Créer les comptes (seed)

À faire seulement si la base est vide (après un down -v). Crée owner/admin/reviewer + les providers factices.

docker compose -f infra/docker-compose.deploy.yml exec backend python -m app.scripts.seed

Comptes : owner@vf.ai, admin@vf.ai, reviewer@vf.ai — mot de passe password123 (à changer ensuite).

10Migrations de base de données

Normalement automatiques au démarrage du backend. En cas de besoin manuel :

# Appliquer les migrations docker compose -f infra/docker-compose.deploy.yml exec backend alembic upgrade head # Voir l'état actuel de la base docker compose -f infra/docker-compose.deploy.yml exec backend alembic current

11Scripts d'administration disponibles

En plus de seed, le backend fournit ces scripts :

# Nettoyage manuel des fichiers intermédiaires d'une série (remplacer 1 par l'ID) docker compose -f infra/docker-compose.deploy.yml exec backend python -m app.scripts.cleanup_series 1 # Rotation des clés de chiffrement docker compose -f infra/docker-compose.deploy.yml exec backend python -m app.scripts.rotate_keys # Générer le SBOM (inventaire des dépendances) docker compose -f infra/docker-compose.deploy.yml exec backend python -m app.scripts.sbom

Le nettoyage est aussi automatique en fin de génération réussie (garde la vidéo finale + le short, supprime le reste).

12Redémarrer / arrêter

# Redémarrer un seul service (ex. nginx après un souci) docker compose -f infra/docker-compose.deploy.yml restart nginx # Tout arrêter (les données Postgres sont conservées) docker compose -f infra/docker-compose.deploy.yml down # Tout arrêter ET SUPPRIMER la base (repartir de zéro) docker compose -f infra/docker-compose.deploy.yml down -v # Démarrer sans reconstruire (plus rapide) docker compose -f infra/docker-compose.deploy.yml --env-file infra/.env up -d
Attention : down -v efface la base Postgres (séries, comptes, etc.). Ne le faire que si on accepte de tout perdre, puis refaire le seed (section 09).

13Entrer dans un conteneur (dépannage)

# Ouvrir un shell dans le backend docker compose -f infra/docker-compose.deploy.yml exec backend /bin/bash # Inspecter la base de données directement (postgres) docker compose -f infra/docker-compose.deploy.yml exec postgres psql -U vf -d videofactory

Remplacez vf et videofactory par les valeurs de votre .env (POSTGRES_USER / POSTGRES_DB).

14Gérer le bucket OVH (AWS CLI)

# Installer awscli (une fois) sudo apt-get install -y awscli # Configurer les identifiants (puis répondre aux questions) aws configure # Lister les objets d'un dossier du bucket aws s3 ls s3://NOM_DU_BUCKET/series/ --recursive --endpoint-url https://s3.eu-west-par.io.cloud.ovh.net # Supprimer tout un dossier aws s3 rm s3://NOM_DU_BUCKET/series/1/ --recursive --endpoint-url https://s3.eu-west-par.io.cloud.ovh.net

Ou simplement depuis l'interface OVH : bucket → sélectionner → supprimer.

15Surveiller la machine (disque, mémoire)

# Espace disque utilisé df -h # Mémoire vive utilisée free -h # Espace consommé par Docker (images, conteneurs, volumes) docker system df # Nettoyer les images et caches Docker inutilisés (libère de l'espace) docker system prune -a
Attention : docker system prune -a supprime les images non utilisées. Les conteneurs en cours ne sont pas touchés, mais il faudra reconstruire au prochain up --build.

16Transférer des fichiers entre le PC et le serveur

# Télécharger un fichier du serveur vers le PC (à lancer depuis le PC) scp -i C:/Users/ToshR/Downloads/ovh_cle_ssh_privee.pem \ ubuntu@57.130.39.132:/chemin/vers/fichier.mp4 C:/Users/ToshR/Downloads/

Utile pour récupérer des fichiers directement, sans passer par le bouton « Télécharger » de l'app.

17Réparer git (si le remote est cassé)

# Voir le remote actuel cd ~/VideoFactory && git remote -v # Le corriger si l'URL est tronquée ou fausse git remote set-url origin https://github.com/bamel222/VideoFactory.git # Si le pull bloque sur des modifications locales git checkout -- <fichier> git pull

18Récapitulatif de l'architecture

ServiceRôlePort interne
nginxPoint d'entrée (port 80 public), route vers frontend + API80
frontendInterface Next.js (React)3000
backendAPI FastAPI (auth, séries, stockage, notifications)3001
workerExécute le pipeline vidéo (files Redis)—
postgresBase de données5432

Fichiers clés sur le serveur : code dans ~/VideoFactory, secrets dans ~/VideoFactory/infra/.env (jamais commité), config nginx dans ~/VideoFactory/infra/nginx.conf.
Où sont stockées les vidéos : dans le bucket OVH (Object Storage, S3-compatible). Le backend « local » de l'app stocke sur le disque du serveur (éphémère, non persistant) — il est recommandé de le désactiver pour ne garder que OVH.
